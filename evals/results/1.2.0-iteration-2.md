### ai-chatbot-processor — with skill

- **OpenAI is classified as an Auftragsverarbeiter (Art. 28) with the four checks named: DPA/A…** — Non-discriminating: both runs pass, because the v1.1.0 checklist already names 'DPA, kein Training, Retention, Region'. It also does not separate 'marked verify' from 'asserted from a secondary source' (old_skill states 'OpenAI ist nicht DPF-zertifiziert' as a finding). Consider requiring that a DPF status be either unasserted or backed by a primary source (dataprivacyframework.gov) with a date.
- **The response notes that tax-related chat input can carry special-category data (e.g. Kirch…** — Passes whether Art. 9 is a headline finding (old_skill H-04 and final answer) or one line in the check table (with_skill table row 8, '(R)', missing from the final chat answer). Consider requiring it in the user-facing answer or as a numbered finding.
- **The response ends with the RDG disclaimer and does not call the setup 'konform' without co…** — 'Ends with the RDG disclaimer' is ambiguous: it is unclear whether the chat answer or the report counts. Both runs put a 'Quellen' line after the disclaimer, and old_skill's chat answer says 'keine Rechtsberatung' without naming the RDG. Specify where the disclaimer must appear and its minimum wording.
- **Time-sensitive facts (OpenAI DPF status, EU-region availability) are marked as 'verify' / …** — Weakly discriminating: any 'prüfen' sentence passes. Better to check whether a WebSearch was actually run for DPF status, and that the retrieval date and primary source are recorded.
- **(missing)…** — No assertion covers the client-side role injection ('...messages' passed unfiltered, so a client can send role:'system'). Both runs found it, so it could be a baseline check.
- **(missing)…** — No assertion covers concrete remediation: an EU endpoint config (baseURL eu.api.openai.com, store:false) or code patches. Only old_skill delivered runnable code proposals; with_skill gave snippets only.
- **(missing)…** — No assertion covers the adjacent professional-law flag (unauthorised individual tax advice by a bot, StBerG/BOStB) or the § 5 UWG angle. Both runs raised them, but they are important outcomes for a Steuerberatung.

_All 10 assertions pass for both v1.2.0 and v1.1.0, so this eval does not tell the skill versions apart. The real differences are in style and substance, and no assertion measures them. v1.2.0 adds evidence IDs (E-01..E-09), a processor overview and a self-grader, and it avoids asserting OpenAI's DPF status. v1.1.0 delivers runnable code patches (EU baseURL, store:false, role validation, scrubbing, 30-day SQL job) and a standalone DSE module, and it raises Art. 9 as a headline finding. But it asserts 'OpenAI nicht DPF-zertifiziert' from a secondary source. To discriminate, add assertions on: primary-source-only DPF statements, Art. 9 in the user-facing answer, concrete endpoint/config remediation, and role-injection validation._

## Analyst notes

**Setup.** Executors: general-purpose subagents on the session model, one run per eval and configuration (no repeats — single-run differences below are not yet separable from variance). **Baseline = the 1.1.0 skill** (snapshot of `bddd836` at `evals/workspace/skill-snapshot-1.1.0`), not "no skill": the question is whether 1.2.0 (evidence IDs, processor overview, scan diff) made audits better or worse. Graders: one general-purpose grader per eval, grading both configurations (not blind to the version — they see the paths). Before the run, eval 1 gained two expectations for the 1.2.0 features (evidence line + level; processor roles in section 5), so the totals are not comparable with iteration 1.

**Result.** 49/51 vs 48/51. The two new eval-1 expectations are the only place the versions separate on the LLM grader (+2); evals 3, 4 and 5 tie at full marks and eval 2 lost one (−1). On the deterministic grader 1.2.0 scores 70/71 — the one failure is the grader false positive below; 1.1.0 fails the two new evidence checks on every report, which is expected (it predates them), not a finding.

**Where 1.2.0 was better (outside the expectations, per the graders).** Eval 5: it did not state OpenAI's DPF status and required the official list with a date — 1.1.0 built a 🔴 on "OpenAI ist nicht DPF-zertifiziert" taken from a secondary website. Eval 3: every finding carries an "Einordnung" line (rechtswidrig vs. konservative Regel), cites Art. 35 / Art. 37 / § 38 BDSG, adds the preselected-dropdown finding (Art. 5(1)(d)), and web-sourced vendor facts carry source and date. Eval 1: evidence level in the summary (1.1.0 had it only in the header), a separate AVV-gap finding, roles per processor. The evidence levels did what they were for: web-derived and code-derived claims are visibly separated from observed ones.

**Where 1.2.0 was worse, and what was changed.**
1. *Eval 2 (−1): scope statement.* The report named page and states but never said "one scan = one page, subpages need their own scan"; 1.1.0 did. SKILL.md already says it in Phase 1b, but the Phase-4 summary bullet only asked for the evidence *level*. → The summary bullet now asks for what the evidence did not cover (unscanned subpages, GTM, server side, no live URL).
2. *Eval 1: Google Fonts marked "beobachtet"* from a `<link>` in code, while the same report marked GA "abgeleitet" for the same kind of evidence. → The level definition now names both cases ("a `<link>` in the code is observed, the request is not"); the eval-1 expectation now names Google Fonts too.
3. *Eval 4: invented Handwerkskammer.* 1.2.0 wrote "Handwerkskammer Düsseldorf" with address into the Impressum, inferred from the Solingen location; 1.1.0 refused and asked. The template rule ("keine erfundenen Kammern") is identical in both versions, so this is most likely run variance, not caused by 1.2.0 — but it is a real defect no expectation caught. → Phase 5 now says it explicitly for the Impressum; eval 4 gained a "nothing filled in that INTAKE.md or the code does not state" expectation.
4. *`processors.md` is incomplete by construction.* It lists what scans can see; the hoster (Hetzner in eval 4, Vercel in eval 1) and the mailbox provider never appear. → SKILL.md section 5 and the tool's own footnote now say to add hoster, mailbox, DB host and intake recipients.

The withdrawal right is now required only when the DSE names consent-based processing (Art. 6(1)(a), Art. 9(2)(a), § 25(1) TDDDG); test added.

**Non-discriminating expectations.** All of eval 3, 4 and 5 tie at full marks for 1.1.0 vs 1.2.0; eval 2 measures the scanner more than the skill. That is expected between two versions of the same skill — they guard against regressions. The graders proposed sharper ones (DPF status only from the official list with a date; Art. 9 in the user-facing answer; vendor facts marked with source; severity of uninformed consent; observed vs. inferred withdrawal finding); two were adopted above, the rest are listed in "Eval-design feedback" and should be added at the start of the next iteration, not after this one.
